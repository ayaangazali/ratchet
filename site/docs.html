How it works

The high-level picture

You give Ratchet a repo and a task file. An agent proposes patches; Ratchet never asks the agent whether it's finished. Instead, every candidate patch runs a seven-stage verifier gauntlet — build, cheat check, hidden fail-to-pass tests, pass-to-pass regressions, types, lint, diff hygiene. Only the gauntlet can declare success, and it does so in exactly one place in the code.

Every step is a git commit plus a sandbox snapshot, so a run is a tree search over repo states with the verifier's score as the value function. Stalled branches fork in parallel, dead ends are pruned (and parked, so they're still restorable), and the winning path exits as one squashed diff at a human approval gate. Every graded node is signed into a tamper-evident receipt chain you can audit.

Getting started

Up and running in 10 minutes

1. Install (2 min)

You need Python 3.11+ and git. Node 22.14+ only if you want the live TrueForge path.

git clone https://github.com/ayaangazali/ratchet && cd ratchet
make dev          # editable install + dev deps

2. Seed the demo and run the suite (3 min)

make demo         # seeds demo-repo/: a broken slugify, three prepared patches
make test         # the whole suite; no docker, no network
make redteam      # the published reward-hacking battery fired at the verifier

3. Get your first three verdicts (3 min)

The honest fix goes green; the cheat is blocked before a line of it runs; the canary hack is caught with zero static findings.

ratchet verify --task tasks/demo-001-slugify/task.yaml --repo demo-repo \
               --diff demo-repo/patches/honest.diff    # GREEN, score 1.000
ratchet verify --task tasks/demo-001-slugify/task.yaml --repo demo-repo \
               --diff demo-repo/patches/cheat.diff     # CHEATED
ratchet verify --task tasks/canary-impossible/task.yaml --repo demo-repo \
               --diff demo-repo/patches/canary_hack.diff  # CHEATED, zero static findings

4. Run a full search, offline (2 min)

make run-offline  # a complete search: root, a real prune, a green node, the gate
make proof        # exercise every claim on the site and keep the evidence
make console      # the TUI
make audit        # verify the latest run's receipt chain

macOS note: the eval script uses GNU timeout — brew install coreutils and put gtimeout on PATH as timeout.

FAQ

Frequently asked questions

Product

What models does Ratchet work with?
Model calls, retries, and multi-provider routing belong to the TrueForge harness Ratchet runs on. Ratchet owns what counts as progress — it is model-agnostic by construction, and the whole verifier runs with no model at all.
Does it need Docker?
No. Ratchet never orchestrates containers. Sandboxes come from the harness; the documented fallback is one git worktree per node off a prebuilt base, with a shared pre-warmed virtualenv.
What are the API limits?
Ratchet itself imposes none — the offline paths (make test, make proof, ratchet verify) make zero API calls. Live runs inherit whatever limits your TrueForge model providers have, and the search budget (nodes, wall-clock, dollars) is set per run and enforced by the scheduler.
Can I add my own verification rules?
Yes. Every new rule ships with two tests — a patch that trips it and a patch that must not — plus an entry in the red-team battery, so the perfect catch score stays honest. See "Extending Ratchet" in the README.
Is there a Slack or CI integration?
Not yet. Today the integration points are the CLI, the TUI console, and the receipt chain (auditable in CI via make audit). The red team already runs in CI on the repo itself.

Billing

How much does Ratchet cost?
Nothing. Ratchet is MIT-licensed open source — every feature on this site is in the public repo. You pay only your own model providers for live runs. See pricing for planned hosted tiers.
Is there a trial, refund, or contract?
No trial needed — the full product is free. Hosted plans, when they ship, will be monthly with no long-term contract.

Security

Can the agent see the held-out tests?
No. Held-out test names never appear in anything the agent can read — the context assembly, the observations, and every bus event are all scrubbed, and there are tests asserting it. A leak would silently destroy the signal, so this is invariant #5 of the project.
What stops the agent from editing the tests or the verifier?
Protected paths are reverted before grading on every run with no skip flag; runtime writes to graded paths are a cheat finding; and the verdict's exit code is echoed outside the region the agent can influence.
Can a run's results be forged after the fact?
Every graded node is signed into a hash-linked receipt chain. make audit re-verifies it; edit one verdict and the chain reports BROKEN with the exact receipt that fails. The tamper demo runs in make proof.
What can the sandbox reach on the network?
On the live harness path, local sandbox egress is allowlisted to PyPI and GitHub only. The offline paths make no network calls at all.

Troubleshooting

`make evals` fails on macOS with a timeout error
The eval script uses GNU timeout. Run brew install coreutils and expose gtimeout on your PATH as timeout — a symlink into your venv's bin/ works.
A patch I believe is honest gets flagged as a cheat
Run ratchet verify on the diff by hand with no model in the loop and read the failing stage — it names the exact rule and location. If you still think the rule is wrong, open an issue with the diff; the verifier only changes with a reproducing test, never to make a specific patch pass.
The search never goes green
Read the failing stage first. Scores below 1.0 tell you which stage is holding the line (f2p means hidden tests still fail). Check the budget line — a run that exhausts its node budget parks its best branch rather than forcing a verdict.
Where did my pruned branch go?
Pruned work is parked before it is dropped, at refs/ratchet/pruned/<node>. A dead end is still a node you can rewind to.

Can't find it? Open an issue — that's the support channel, and it's read.
